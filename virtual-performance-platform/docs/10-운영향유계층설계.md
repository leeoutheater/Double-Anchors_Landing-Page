## 0. 위치와 범위 (Where this sits)

```
 [신규] L9  공공·책무성       예산·심사·성과·접근성·감사
 [신규] L8  향유             시민 향유 뷰어·개방형 과정관극·시연홍보·참여
 [확장] L7  운영             운영조직(상주단체)·시즌·대관·예산·콜시트·공론의 장
 ────────────────────────── 이상 본 문서의 설계 대상 ──────────────────────────
 [계승] L0~L6  제작·검증 엔진  데이터모델·시연뷰어·Reverse·GH·TD·Unreal·MVR/GDTF
```

- **운영(L7 확장):** 가상극장을 *조직처럼 운영* — 누가, 무엇을, 언제, 얼마에.
- **향유(L8):** 시민이 *과정부터* 보고, 참여하고, 누린다.
- **책무성(L9):** 운영·향유의 모든 결정·예산·성과를 추적·공개.
- **F9 정합:** standalone HTML은 *시연 제작·뷰어 클라이언트*로 계승. 운영·향유는
  다중사용자·영속성이 필요하므로 **경량 백엔드 계층을 신설**(§7). 충돌 아님.

## 1. 설계 원칙

1. **단일 시연본 / 다중 뷰:** 같은 작품을 운영은 일정·예산으로, 시민은 향유로 본다.
2. **과정의 가상화·자료화 → 향유 직결:** 제작 과정이 곧 향유·교육·아카이브 콘텐츠.
3. **검증 = 홍보:** 공론·시연의 산출물이 그대로 홍보·향유 자산.
4. **공공 책무성:** 모든 운영·예산·심의 결정은 감사 가능(AuditLog).
5. **공개도 제어:** 비공개(내부)↔관계자↔시민공개를 단계·요소별로 설정.

## 2. 운영 계층 (Operation, L7)

### 2.1 운영조직 모델 (Producing-House)

```
가상극장 운영체(Organization)
   └─ 상주단체(ResidentCompany) ×N        ← 입주 공연단체·예술가
        └─ 작품/프로덕션(Production) ×N    ← 시즌에 편성
             └─ 시연본(제작 엔진 L0~L6 산출)
```

- 플랫폼은 *상설 공연단체를 보유한 제작 조직*처럼 작동. 상주단체는 시즌·레퍼토리·
  제작 사이클을 운영한다.

### 2.2 역할·권한 (RBAC) — 단일 데이터, 역할별 뷰

| 역할 | 소속 | 핵심 권한 | 주 뷰 |
|------|------|-----------|-------|
| 예술감독 | 운영체 | 시즌 편성·작품 승인 | 운영 콘솔 |
| 프로듀서/제작PD | 상주단체 | 작품 생성·예산·일정·인력 | 운영 콘솔 |
| 무대감독 | 작품 | 큐시트·콜시트·리허설 | 제작(시연) |
| 디자이너(조명/음향/영상/무대) | 작품 | 해당 파트 시연 편집(동일 권한) | 제작(시연) |
| 운영/행정 | 운영체 | 대관·정산·아카이브 | 운영 콘솔 |
| 심사위원(공공) | 외부 | 공론 열람·평가(편집 불가) | 공론 광장 |
| 시민 | 공개 | 향유·과정 관극·피드백 | 향유 포털 |

> 기존 NOTE 요구("무대감독·조명/음향/영상 디자이너 동일 권한")를 RBAC에 반영.

### 2.3 작품 생애주기 상태기계 (Production Lifecycle)

```
 기획 ─→ 제작(시연) ─→ 공론(심의) ─→ 편성·운영 ─→ 공연 ─→ 아카이브
  │         │             │            │          │        │
 컨셉·     시연본       공개 검증     대관·예산   실연      과정·실연
 예산초안   구성·검증    ·지원심사    ·콜시트     ·향유     자료화
```

각 전이는 **권한·완료조건·공개도**를 가진다. (예: 공론→편성 전이는 심사 통과 +
극장 트윈 안전검증(참고용) 확인 필요)

### 2.4 대관·일정 (Booking & Scheduling)

- **블랙박스 메타극장 / 극장 디지털 트윈 예약:** 트윈(L0)·메타공간 슬롯 예약
- **테크니컬 라이더 매칭:** 작품 요구(L6 MVR/GDTF·무대기계)와 극장 사양 자동 대조
- 셋업·리허설·공연·철수 일정, 충돌 검사

### 2.5 예산·정산 (Budget & Settlement)

- 시연 자원(인력·장비·시간·공간, [02]) → 예산 항목 자동 매핑
- 시나리오별 비교, 집행 추적(Ledger), **감사 로그**
- 결제·정산 자체망은 초기 비범위(외부 연동) — [DECISIONS D8]

### 2.6 인력·자원 (Call Sheet)

- 시연 기반 콜시트(역할·인원·장비·시간), 알림·확인

### 2.7 공론(公論)의 장 (Public Forum) — 운영과 향유의 경첩

- **흐름:** 지원사업 공모 → 시연본 제출 → 공개 심의(평가 루브릭 + 질의·코멘트 +
  시민 열람) → 결정·사유 기록(책무성)
- 동료 평가(peer review) + 행정 투명성. 공론 기록 = L9 책무성 근거.
- 공개도: 심의 과정은 관계자, 결과·요지는 시민 공개(설정 가능).

## 3. 향유 계층 (Enjoyment, L8)

### 3.1 개방형 과정 관극 (Open-Process Spectatorship)

- 작품 단계별 **공개도 설정**(연습/시연/공론 각각 비공개·관계자·시민공개)
- 과정 타임라인·비하인드·자료화본을 시민이 관극
- "만들어지는 과정"이 콘텐츠·교육·아카이브로 동시 기능

### 3.2 시연 기반 홍보 (Promotion from Pre-visualization)

- 시연본 → 티저·키비주얼·예고 **자동 추출**
- 관심도·알림·예매 연계, 캠페인 페이지(제작과 병행)

### 3.3 시민 향유 뷰어 (Citizen Viewer)

- 무설치 웹 사전 체험(시연본 임베드)
- **좌석별 사이트라인 미리보기** — 기존 L1 뷰어·*극장기준점*·트윈 재사용
- 배리어프리·접근성 정보, 다국어 자막

### 3.4 참여·피드백 (Participation)

- 사전 반응·투표·코멘트 → 작품성·대중성 검증([00] ①축) + 정책 판단으로 환류

## 4. 데이터 모델 (신규 엔티티 — L0 Zod 스키마 확장)

```

Organization ──< Season ──< (Production 편성)
Production ──< stateMachine(기획|제작|공론|운영|공연|아카이브)

Production ──< CallSheet ──< CallItem
Production ──< BudgetPlan ──< BudgetLine ; Ledger(집행)

Production ──< PublicPage(향유) ──< ProcessLog(과정관극 단계·공개도)

```

## 5. 화면·정보구조 (Role-based IA)

```
운영 콘솔 (예술감독/PD/행정)
├─ 시즌·레퍼토리 편성
├─ 상주단체·작품(상태기계)
├─ 대관·일정(트윈/메타극장 슬롯·라이더 매칭)
├─ 예산·정산(시나리오·집행·감사)
└─ 콜시트·인력

공론 광장 (심사위원/관계자/시민열람)
├─ 공모·제출 작품 목록
├─ 시연본 + 평가 루브릭 + 질의/코멘트
└─ 결정·사유 기록

시민 향유 포털 (공개)
├─ 공연/작품 탐색
├─ 사전 체험(시연 임베드) + 좌석 시야 + 접근성
├─ 과정 관극(연습~시연 타임라인)
└─ 관심·피드백·예매 연계

공공 대시보드 (정부/기관)
└─ 예산 타당성·성과·향유/접근성 지표·책무성 리포트
```

## 6. MVP 범위 (운영·향유 최소 고리)

**한 문장:** "운영체가 상주단체의 한 작품을 시즌에 편성→상태기계로 진행하고,
공론 광장에서 공개 검증을 받고, 시민 향유 포털에서 과정·사전 체험을 공개해
관심·피드백을 받는다."

| 영역 | MVP 포함 | 제외(후속) |
|------|----------|-----------|
| 운영 | 조직/상주단체/작품 + 상태기계 + 대관(트윈 슬롯) + 예산 리포트 + RBAC | 정산 결제 내재화, 정밀 콜시트 |
| 공론 | 공모→제출→공개 심의(루브릭+코멘트)→기록 | AI 심사 보조 |
| 향유 | 공개 향유 페이지 + 사전 체험(시연 임베드) + 사이트라인 미리보기 + 관심/피드백 | 라이브 송출, 추천 |
| 책무성 | AuditLog + 기본 지표 | 고급 성과분석 |

## 7. 기술 구현 (F9 정합)

| 구성 | 방식 |
|------|------|
| 시연 제작·뷰어 | **standalone HTML 계승(F9)** — 변경 없음, 임베드/연동만 추가 |
| 운영·향유 백엔드 | **경량 서버 신설** — 기존 `convert-server`(FastAPI) 패턴 확장 또는 별도 서비스. 인증·RBAC·영속성(DB) |
| 데이터 | L0 Zod 스키마 ↔ DB(초기 SQLite → Postgres). 감사 로그 |
| 시민 향유 포털 | 공개 정적 + API. 시연본은 standalone 뷰어 임베드 |
| 사이트라인 | 기존 L1 뷰어·극장기준점·트윈 재사용(서버 렌더 옵션) |

> ⚠️ **결정 필요:** 운영·향유는 다중사용자·영속성이 필수 → 백엔드 도입은 불가피.
> 이는 F9(제작 클라이언트=standalone)와 별개 결정. → [DECISIONS D15]

## 8. 단계 계획 (Operation·Enjoyment Phasing)

- **A. 토대:** 데이터모델 + 인증/RBAC + 조직/상주단체/작품 + 상태기계
- **B. 운영:** 대관(트윈 슬롯)·예산 리포트·콜시트
- **C. 공론:** 공모→제출→공개 심의→기록
- **D. 향유:** 시민 포털 + 사전 체험 + 사이트라인 + 과정관극 + 시연홍보
- **(병행)** L1 Brep 패치([09])는 별도 트랙으로 진행

## 9. 미결·의사결정 (→ DECISIONS.md)

- **D15** 운영·향유 백엔드 도입(영속성·인증) — F9와 별개

- **D18** 개방형 과정관극 기본 공개도(디폴트 비공개/관계자/공개)

## 10. 의뢰자(도메인 전문가) 검수 포인트

1. **운영조직 역할·권한**이 실제 극장 조직(예술감독·제작PD·무대감독·디자이너·
   행정)과 정합하는가
2. **공론의 장 심의 루브릭** 항목(작품성·대중성·구현가능성·안전·예산 타당성의
   배점·문항)
3. **대관·테크니컬 라이더** 워크플로우가 현장 관행과 맞는가
4. **개방형 과정관극**의 공개 범위가 창작 보호와 양립하는가
